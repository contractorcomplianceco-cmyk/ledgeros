Build a fully functioning production-intent custom accounting system for CCA called LedgerOS.

LedgerOS is not a demo, mockup, fake dashboard, static prototype, or UI-only app. The goal is to build a real, working accounting application that can eventually replace Zoho Books after proper migration, reconciliation, security review, and approval.

LedgerOS must be highly intuitive, customizable, role-aware, audit-friendly, and designed to integrate with the company’s broader app ecosystem.

Company context:
- Current accounting platform is Zoho Books.
- Founder direction is to replace Zoho Books with LedgerOS.
- Bank source is Navy Federal Credit Union.
- LedgerOS must be allowed to create accounting records/actions, not just display reports.
- Christin is the primary day-to-day accounting operator.
- Rose and Christin are the accounting approvers.
- Command Center should receive analytics and overviews only.
- Command Center must not become the accounting workspace or full ledger.
- Sensitive/private boundaries are not fully defined yet, so default to restrictive access.
- Existing related systems include Command Center, Client Portal / Online Services, ComplianceConnect, Zoho CRM, Zoho Forms, Zoho Billing, RUN ADP, Tara OS, Sales Intelligence OS, Guided Sales, Business Services Hub, QualifierConnect, Bid Intelligence OS, Facility Intelligence, HealthCast, and TrustScore.

Important product rule:
Build LedgerOS as a real accounting system with persistent data, real workflows, role-based permissions, approval gates, audit logging, and integration-ready architecture. Do not use fake success states. Do not show “uploaded,” “sent,” “synced,” “posted,” or “paid” unless the action actually happened in the app’s backend.

Technology expectations:
- Use a modern full-stack app architecture.
- Use persistent database storage.
- Use server-side APIs for all accounting actions.
- Use server-side validation for accounting rules.
- Use role-based access control.
- Use audit logging.
- Use clean, maintainable code.
- Use seed data only for development/testing and label it clearly as test data.
- Include a clear path to connect real integrations later.
- Do not hardcode secrets.
- Use environment variables for secrets and connection settings.
- Build with production intent, even if some external integrations start as import/export workflows.

Design requirements:
- Build the usable app as the first screen after login.
- Do not create a marketing landing page.
- Make it feel like a serious accounting cockpit: clean, calm, dense, professional, fast to scan.
- Avoid decorative gradients, oversized hero sections, and marketing-style cards.
- Use restrained colors, clear hierarchy, and practical controls.
- Use tables for accounting records.
- Use filters, tabs, search, saved views, and status chips.
- Use drawer/detail panels for record review.
- Use modals only for focused actions.
- Use icons for common actions where appropriate.
- Keep all text readable on desktop and mobile.
- Make the interface responsive.
- Do not let tables overflow awkwardly on small screens; provide horizontal scroll or responsive row cards.
- Every empty state must tell the user what action to take next.
- Every error state must explain what failed and what can be done.

Security requirements:
- Require authentication.
- Require role checks on the server, not only in the UI.
- Require MFA-ready architecture for Owner, Accounting Lead, Accountant, and Systems Reviewer.
- Create audit logs for every create, edit, delete, approve, reject, post, reconcile, export, permission change, login, integration event, import, and settings change.
- Store timestamps, user ID, action type, record type, record ID, before/after values when applicable, source IP/session if available, and reason/note if required.
- Do not expose bank account numbers except masked display.
- Do not expose payroll/compensation details to unauthorized roles.
- Create restrictive defaults for sensitive data.

Required accounting behavior:
- Debits and credits must balance before a journal entry can be posted.
- Posted entries cannot be silently edited.
- Corrections to posted entries must use reversal or adjusting entry workflows.
- Locked periods cannot be edited by ordinary actions.
- Locked period changes require adjusting entries and approval.
- Invoices must move through Draft → Submitted → Approved → Sent/Posted.
- Payments must be matched to invoices and/or bank transactions.
- Bills must move through Draft → Submitted → Approved → Paid.
- Expenses must require receipt or explicit missing-receipt approval.
- Bank transactions must remain Pending Review until categorized/matched.
- Reconciliation must compare starting balance, ending balance, cleared transactions, and variance.
- Monthly close must have a checklist and lock period function.
- Every financially meaningful action must create an audit log.

Banking workflow:
1. User clicks Banking.
2. User clicks Add Bank Account.
3. User selects Navy Federal Credit Union.
4. User selects connection method:
   - Secure bank connection placeholder
   - CSV import
   - Manual transaction entry
5. User enters masked account label.
6. User saves bank account.
7. User clicks Import Transactions.
8. User uploads CSV or uses test import.
9. System creates Pending Review transactions.
10. User clicks a transaction.
11. System shows suggested match/category/confidence.
12. User clicks Match, Categorize, Split, Mark Transfer, Attach Receipt, or Send to Review.
13. System updates status.
14. User clicks Reconcile.
15. User selects statement period.
16. User enters starting balance and ending balance.
17. User selects cleared transactions.
18. System calculates variance.
19. User clicks Submit Reconciliation for Approval.
20. Rose or Christin approves.

Invoice workflow:
1. User clicks Invoices.
2. User clicks New Invoice.
3. User selects customer.
4. User selects source app/product.
5. User adds line items.
6. User sets due date/payment terms.
7. User attaches support.
8. User clicks Preview.
9. User clicks Save Draft.
10. User clicks Submit for Approval.
11. Rose or Christin clicks Approve.
12. User clicks Send Invoice.
13. System posts AR entry.
14. System logs activity.
15. Command Center receives summary only.

Payment workflow:
1. User clicks Payments.
2. User clicks Record Payment.
3. User selects customer/invoice.
4. User enters amount/date/method/reference.
5. User selects deposit account.
6. User clicks Match to Bank Transaction.
7. User selects matching Navy Federal deposit.
8. User clicks Preview Accounting Impact.
9. User clicks Post Payment if allowed.
10. System updates invoice status.
11. System updates AR aging.
12. System creates audit log.

Bills/AP workflow:
1. User clicks Bills.
2. User clicks New Bill.
3. User selects or creates vendor.
4. User enters bill date/due date/amount/category.
5. User tags client/project/product if applicable.
6. User uploads bill or receipt.
7. User clicks Detect Duplicates.
8. User clicks Save Draft.
9. User clicks Submit for Approval.
10. Rose or Christin approves/rejects/requests changes.
11. User records payment.
12. Payment is matched to bank transaction.

Expense workflow:
1. Team member clicks Expenses.
2. Team member clicks Submit Expense.
3. User enters date/vendor/amount/category/client/project/app source.
4. User uploads receipt.
5. User clicks Submit.
6. Christin clicks Review Expenses.
7. Christin opens expense.
8. Christin clicks Approve, Reject, Request Receipt, Split Category, or Mark Non-Reimbursable.
9. Approved expense creates accounting entry/draft according to approval settings.
10. Command Center receives status summary only.

Payroll workflow:
1. User clicks Payroll.
2. User clicks Import RUN ADP Summary or Add Payroll Summary.
3. User enters payroll period/date/summary totals.
4. System restricts employee-level details by permission.
5. System flags unusual payroll changes.
6. Christin clicks Submit Payroll Review.
7. Rose or Christin approves.
8. System creates summarized ledger entries or draft entries according to settings.

Journal entry workflow:
1. User clicks Ledger.
2. User clicks Journal Entries.
3. User clicks New Journal Entry.
4. User enters date/memo/reason.
5. User adds debit lines.
6. User adds credit lines.
7. System blocks unbalanced entry.
8. User attaches support.
9. User clicks Preview Impact.
10. User clicks Submit for Approval.
11. Rose or Christin approves and posts.
12. If correction is needed, user must create reversal or adjusting entry.
